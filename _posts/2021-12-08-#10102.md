## Notes

Currently bitcoin code always run within a single process. If you are using
`bitcoind` node and wallet code execute together in the same process so, for
example, a crash in wallet code could bring down the node, or a vulnerablility
in the node could directly expose wallet data. If you are using `bitcoin-qt`
node, wallet, and GUI code all runs in the same process, so the same things are
true, and additionally the GUI is tied in, so it's not possible to start and
stop the GUI independently of the node and wallet, or run it on different
machines, or make it more robust against crashes and vulnerabilities.

PR [#10102](https://github.com/bitcoin/bitcoin/pull/10102), combined with the
`--enable-multiprocess` build option, builds a new `bitcoin-node` executable
that can be used as a drop in replacement for `bitcoind`, and a new
`bitcoin-gui` executable, that can be used a drop-in replace of the
`bitcoin-qt`, with no changes in features or usage, except that internally they
will use multiple processes, and process separation.

Specifically, `bitcoin-node` will internally spawn a `bitcoin-wallet` executable
to run wallet code. Two two processes will communicate across a socket, with the
node code controlling the wallet with
[`interfaces::WalletClient`](https://github.com/bitcoin/bitcoin/blob/b8cc75435a0bcb6c62083ff134b1ba3d2ace50d1/src/interfaces/wallet.h#L310-L313)
methods, and the wallet code calling the node with
[`interfaces::Chain`](https://github.com/bitcoin/bitcoin/blob/b8cc75435a0bcb6c62083ff134b1ba3d2ace50d1/src/interfaces/chain.h#L92)
methods. Similarly `bitcoin-gui` will internally spawn a `bitcoin-node` process,
and control it by calling
[`interfaces::Node`](https://github.com/bitcoin/bitcoin/blob/b8cc75435a0bcb6c62083ff134b1ba3d2ace50d1/src/interfaces/node.h#L63-L64)
methods, and control wallets by calling
[`interface::Wallet`](https://github.com/bitcoin/bitcoin/blob/b8cc75435a0bcb6c62083ff134b1ba3d2ace50d1/src/interfaces/wallet.h#L52-L53)
methods.

#10102 adds the plumbing that allows this cross process communication to work
transparently, *without changing existing code, only adding new code*. This is
possible because all the interfaces in `src/interfaces/` (`interfaces::Chain`,
`interfaces::Node`, `interfaces::Wallet`, `interfaces::Init`) are all abstract
classes with virtual methods, so different implementations of all the interfaces
can be substituted with no changes to calling code. The PR adds new
implementations of all these interfaces providing multiprocess support. In early
versions of this PR this required adding a lot of boilerplate code. Every method
in every interface, and every argument and return value of every method had to
had custom C++ code written that would handle the method call serialization and
forwarding from the calling process to the called process. For example, the
[`Wallet::encryptWallet`](https://github.com/ryanofsky/bitcoin/blob/pr/ipc.19/src/ipc/interfaces.h#L275)
abstract method:

```c++
    virtual bool encryptWallet(const SecureString& wallet_passphrase) = 0;
```

had a
[`ipc::capnp::WalletImpl::encryptWallet`](https://github.com/ryanofsky/bitcoin/blob/pr/ipc.19/src/ipc/capnp/interfaces.cpp#L205-L213)
implmentation forwards the encrypt call to the wallet process using the [Cap'n
Proto RPC framework](https://capnproto.org/cxxrpc.html):

```c++
    bool encryptWallet(const SecureString& wallet_passphrase) override
    {
        auto call = MakeCall(m_loop, [&]() {
            auto request = m_client.encryptWalletRequest();
            request.setWalletPassphrase(ToArray(wallet_passphrase));
            return request;
        });
        return call.send([&]() { return call.m_response->getResult(); });
    }
```

with corresponding code in a [`ipc::capnp::WalletServer::encryptWallet`
method](https://github.com/ryanofsky/bitcoin/blob/pr/ipc.19/src/ipc/capnp/server.cpp#L102-L107)
in the wallet process to handle the incoming RPC:

```c++
    kj::Promise<void> encryptWallet(EncryptWalletContext context) override
    {
        context.getResults().setResult(
            m_impl->encryptWallet(ToSecureString(context.getParams().getWalletPassphrase())));
        return kj::READY_NOW;
    }
```

by forwarding it to the local [`ipc::local::WalletImpl::encryptWallet`
method](https://github.com/ryanofsky/bitcoin/blob/c4e2c92f790b7e86c3f7095ef37c79f77b44cc6f/src/ipc/local/interfaces.cpp#L150-L153):

```c++
    bool encryptWallet(const SecureString& wallet_passphrase) override
    {
        return m_wallet.EncryptWallet(wallet_passphrase);
    }
```

which is the same method that would be called directly if code were running in a
single process instead of multiple processes.

Because the
[`ipc::capnp::WalletImpl::encryptWallet`](https://github.com/ryanofsky/bitcoin/blob/pr/ipc.19/src/ipc/capnp/interfaces.cpp#L205-L213)
and
[`ipc::capnp::WalletServer::encryptWallet`](https://github.com/ryanofsky/bitcoin/blob/pr/ipc.19/src/ipc/capnp/server.cpp#L102-L107)
and similar method just contain boilerplate code forwarding calls and
serializing arguments and return values, these are now automatically generated
and no longer part of this PR (but if you build the PR you will see this in
generated code). The advantage of code generation is that if an interface method
is added or changed, supporting IPC only requires updating a single line in the
interface's
[`.capnp`](https://github.com/ryanofsky/bitcoin/blob/pr/ipc.167/src/ipc/capnp/wallet.capnp#L20)
file:

```capnproto
    encryptWallet @1 (context :Proxy.Context, walletPassphrase :Data) -> (result :Bool);
```

and all the corresponding C++ IPC and forwarding code will be generated from
that.

The support for this was added previously in [#19160 Multiprocess: Add basic
spawn and IPC support](https://github.com/bitcoin/bitcoin/pull/19160) ([review
club](https://bitcoincore.reviews/19160)), so the most significant part of 10102
is just adding `.capnp` interfaces for all the interfaces in
[`src/ipc/capnp/`](https://github.com/ryanofsky/bitcoin/tree/pr/ipc.167/src/ipc/capnp).
